# Offline-first PWA

The P5 deliverable this covers: *"Offline-first PWA. Manifest, service
worker, IndexedDB write queue, conflict-safe sync on reconnect. A
technician must be able to scan a passport, run an assessment against a
cached model or a queued request, and record a removal with no network at
all."*

> **Status.** The manifest, service worker, app-shell precaching, cached
> passport/component lookups, and the IndexedDB write queue with
> reconnect-triggered sync are all built, verified via a production build
> (`npm run build` generates `dist/sw.js` and `dist/manifest.webmanifest`)
> and covered by a real IndexedDB-backed test suite
> (`frontend/src/test/offline.test.js`, using `fake-indexeddb` since jsdom
> has no native IndexedDB). One piece of the original wording is only
> partly true - see §3.

---

## 1. What "offline" means here, piece by piece

| Requirement | How it is met |
|---|---|
| PWA manifest and installable app shell | `vite-plugin-pwa` (`frontend/vite.config.js`), icons in `frontend/public/pwa-*.png` (generated from the existing favicon) |
| Service worker with an offline app cache | Workbox, generated by the same plugin - precaches every JS/CSS/HTML/image asset so the app *opens* with no network at all |
| Offline passport/component lookup against a cached record | Workbox `NetworkFirst` runtime caching on `/api/v1/passports/*` and `/api/v1/components*` - a service worker intercepts same-origin requests regardless of whether they were issued via `fetch()` or axios's XHR, so this works transparently for every existing API call, no extra code needed in the API client |
| IndexedDB write queue for assessments, service events and removals | `frontend/src/offline/db.js` + `outbox.js` - a real IndexedDB store (via `idb`), wired into `componentsApi.create`, `addServiceEvent`, `predict`, and `recoveryApi.createItem` in `frontend/src/api/client.js` |
| Conflict-safe sync on reconnect, with a visible pending-sync state | `frontend/src/hooks/useOfflineSync.js` (listens for the browser's `online` event and replays the queue) + `frontend/src/components/OfflineBanner.jsx` (shown in both the authenticated app shell and the standalone QR-scan passport route) |
| Native camera scan path with the manual fallback retained | Pre-existing (`frontend/src/components/QRScanner.jsx`) - always renders the manual lookup, the camera is strictly progressive enhancement on top |

## 2. What "conflict-safe" means for this system's writes, specifically

This system's writes are overwhelmingly *appends* - register a component,
log a service event, list a recovered part, run an assessment. "Last write
wins" is not a meaningful conflict model for an append; there is nothing to
overwrite. The one real conflict shape - a duplicate serial number entered
twice while offline, or a recovery match someone else already accepted
before this device reconnected - surfaces as the backend's own 409/422
response. `syncOutbox` (`frontend/src/offline/outbox.js`) marks that entry
`failed` with the server's own reason and stops there: no queued write is
ever applied twice, and no conflict is ever hidden from the technician who
has to resolve it. That is the guarantee this design actually gives, stated
precisely rather than borrowing "conflict-safe" language from a
merge-two-edits system this domain's write shapes do not need.

Tested in `frontend/src/test/offline.test.js`:

- a queued write replays and clears on success,
- a server-rejected write (409) is marked failed with the server's reason,
  not discarded or silently retried,
- a still-offline replay attempt leaves every entry pending rather than
  losing any of them,
- a failed entry is never re-synced without an explicit retry.

## 3. The one place the original wording is only partly true

*"Run an assessment against a cached model"* - the request to run an
assessment is queued and replayed once back online
(`componentsApi.predict` in `frontend/src/api/client.js`), but **the
Random Forest itself does not run inside the browser**. Shipping the
actual model to run client-side (via ONNX Runtime Web or a WASM build of
the scikit-learn pipeline) was not attempted in this pass - that is real,
separate frontend/ML engineering, not a queueing problem. The honest
behaviour today: a technician who requests an assessment with no signal
sees it queued, not a mocked or client-computed result presented as real.

## 4. Reproducing this

```bash
cd frontend
npm run build   # generates dist/sw.js, dist/manifest.webmanifest, dist/workbox-*.js
npm test        # includes frontend/src/test/offline.test.js
```

To see it live: `npm run preview`, open the built app in a browser, use it
once online (so Workbox caches the passport/component responses), then use
the browser devtools' "Offline" network throttling and confirm a
previously-viewed passport still loads and a new service event queues
instead of failing outright.
