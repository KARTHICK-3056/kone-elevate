# Machine learning

> **This prototype is not trained on proprietary KONE data.**
>
> No real KONE service, inspection, sensor or removal records were available to
> this project. The model is trained entirely on a synthetic degradation
> dataset generated by `backend/app/ml/generate_dataset.py`, which is committed
> in full and reproducible from seed 42. Every metric below describes
> performance on *simulated* degradation.

---

## 1. The task

Multi-class classification. Given the recorded condition of a removed or
in-service elevator component, recommend one of four categories:

| Code | Display name | Meaning |
|---|---|---|
| `CONTINUE_USING` | Continue Using – No Changes Required | Still suitable for its current device and application; keeps operating there unchanged. Never moved elsewhere, sold or transferred. |
| `COMPONENT_RECOVERY` | Component Recovery | Usable individual sub-components are recovered after inspection and testing, for technically suitable lower-demand applications. The complete component is not refurbished or supplied again. |
| `MATERIAL_RECOVERY` | Material Recovery | Useful material is recovered from the end-of-life component. |
| `DISPOSE` | Dispose | Only when none of the other three is technically suitable. |

The category is chosen by a four-gate decision flow (`app/ml/decision_flow.py`),
evaluated in order - never an age rule:

1. **Suitable for its current application?** The calibrated classifier's most
   likely class is Continue Using *and* the inspection score is not in the
   replace band (≤ 48 vetoes). → Continue Using.
2. **Usable sub-components recoverable?** The type is an assembly of separable
   sub-components (a wire rope is not), and the classifier
   judges the parts serviceable (P(continue) + P(component recovery) ≥ 0.5).
   Parts are named only from the component's *recorded* material grade;
   otherwise the wording stays generic. → Component Recovery.
3. **Useful material recoverable?** From the metal share of the recorded
   grade's bill of materials, or else whether the primary material has an
   established recovery route (composites do not). → Material Recovery.
4. Otherwise → Dispose.

The training labels follow the same flow (`decision_flow.label_from_wear`),
applied to the simulator's latent wear.

The output is **advisory**. It is a decision-support signal for a technician
who would otherwise scrap a component for lack of evidence, not an autonomous
authorisation.

## 2. Why Random Forest

| Requirement | Why Random Forest fits |
|---|---|
| Mixed feature types | Handles the 11 numeric + 2 categorical features without scaling |
| Non-linear thresholds | Degradation has knees (a vibration limit, a design-life boundary) that trees capture natively |
| Calibrated-ish confidence | `predict_proba` gives a usable class distribution; tree vote share is a meaningful confidence proxy |
| Explainability | Gini importance is directly inspectable; no post-hoc surrogate model needed |
| Small-data robustness | Works well at 10k records without the tuning burden of gradient boosting |
| Auditability | A deterministic, seeded forest reproduces exactly - which matters when a recommendation lands in an audit chain |

Alternatives considered and rejected for this stage: a single decision tree
(too high-variance), logistic regression (cannot express the threshold
behaviour), gradient boosting (better ceiling but more tuning and less stable
importance for the same prototype value), and a neural network (no data volume
justification and worse explainability for a safety-adjacent workflow).

## 3. Features

13 features, defined once in `app/ml/features.py` and shared by the generator,
the trainer and the inference path. That single contract is what prevents
train/serve skew.

**Categorical (2)** - one-hot encoded with pinned categories:

- `component_type` - 8 levels
- `material` - 6 levels

**Numeric (11)** - passed through unscaled (trees are scale-invariant):

| Feature | Unit | Degradation direction |
|---|---|---|
| `component_age` | years | higher is worse |
| `operating_hours` | hours | higher is worse |
| `load_cycles` | cycles | higher is worse |
| `average_load` | kg | higher is worse |
| `vibration` | mm/s RMS | higher is worse |
| `temperature` | degrees C | higher is worse |
| `service_count` | visits | higher is **better** |
| `repair_count` | repairs | higher is worse |
| `failure_history` | events | higher is worse |
| `inspection_score` | 0-100 | higher is **better** |
| `days_since_last_service` | days | higher is worse |

### Excluded to avoid target leakage

`health_score` is **never** a model feature. It is a deterministic function of
the same raw inputs, so feeding it in would leak an aggregate of the signal and
inflate metrics without adding information. It is computed independently for
explanation purposes only.

`latent_degradation` - the hidden variable the generator uses to produce the
label - is dropped before training. `train.py` asserts that neither column can
appear in `FEATURE_COLUMNS` and fails loudly if a future edit reintroduces one.

## 4. Synthetic data generation

`generate_dataset.py` is a small causal simulator, not a random-number dump:

```
building traffic (duty)   ─┐
maintenance quality       ─┤
environmental stress      ─┼──►  latent WEAR  ──►  noisy observations
component age             ─┤     (never seen         vibration
load stress               ─┘      by the model)      temperature
                                       │             inspection score
                                       │             repairs / failures
                                       ▼
                           disposition policy  ──►  LABEL
```

1. **Hidden drivers.** Duty (lognormal, right-skewed: a few very busy
   installations), maintenance quality (beta), environmental stress (beta).
2. **Usage accumulates** from age x duty against a type-specific design
   envelope, so operating hours and load cycles are correlated with each other
   and with age - as they are in reality.
3. **Latent wear** is a weighted function of usage ratio, cycle ratio, age
   ratio, load stress, maintenance quality and environmental stress, plus
   Gaussian noise.
4. **Observations are noisy views of wear.** Vibration scales with wear times a
   lognormal factor; the inspection score is `100 - 78 x wear` plus noise;
   repairs and failures are Poisson draws whose rate rises with wear.
5. **The label** comes from thresholding wear, adjusted by policy: stricter for
   safety-critical types (+0.065) and electronics (+0.045), more lenient for
   structural steel (-0.055).
6. **Label noise.** 5.5% of labels move one class up or down, modelling the
   real inconsistency between inspectors, sites and years.

### Why the model does not score 100%

Two mechanisms, both deliberate:

- The model sees only *noisy observations* of latent wear, never wear itself,
  and part of the wear (environmental stress, maintenance quality) is never
  observable at all.
- Adjacent-class label noise puts an irreducible ceiling on accuracy.

The result is a realistic 82% rather than a suspicious 99%. A prototype that
reported near-perfect accuracy would be evidence of leakage, not of quality.

### Realistic relationships encoded

- Higher age, hours, cycles, vibration and temperature all increase degradation.
- More preventive maintenance improves condition (and earns a bounded credit in
  the health score).
- Repeated repairs correlate with higher degradation risk.
- Poor inspection scores correlate strongly with poor outcomes - which is why
  `inspection_score` is the top feature by importance.

### Configuration

```bash
python scripts/generate_data.py                          # 10,000 records, seed 42
python scripts/generate_data.py --records 25000 --seed 7
python scripts/generate_data.py --noise 1.4              # harder, noisier task
python scripts/generate_data.py --types Motor "Steel Rope"
```

Outputs `data/synthetic/dataset.csv` plus a stratified `train.csv` / `test.csv`
split.

## 5. Preprocessing and training

The entire preprocessing chain lives **inside** a scikit-learn `Pipeline`, and
the whole pipeline is wrapped in a `CalibratedClassifierCV` before
serialisation. Inference therefore always applies exactly the transformation
and calibration training used - there is no separate, drift-prone transform
step at serving time.

```python
base_pipeline = Pipeline([
    ("preprocessor", ColumnTransformer([
        ("categorical", OneHotEncoder(categories=PINNED, handle_unknown="ignore"),
         ["component_type", "material"]),
        ("numeric", "passthrough", NUMERIC_FEATURES),
    ])),
    ("classifier", RandomForestClassifier(
        n_estimators=400,
        max_depth=16,
        min_samples_split=8,
        min_samples_leaf=3,
        max_features="sqrt",
        class_weight="balanced_subsample",
        random_state=42,
    )),
])

calibrated = CalibratedClassifierCV(base_pipeline, method="isotonic", cv=5)
calibrated.fit(x_dev, y_dev)
```

- **Pinned categories** mean the encoded column order cannot shift between
  runs; `handle_unknown="ignore"` keeps inference alive if an unseen category
  ever arrives.
- **`class_weight="balanced_subsample"`** compensates for `DISPOSE` being the
  smallest class (it is reserved for material with no recovery route).
- **`max_depth=16` and `min_samples_leaf=3`** constrain the forest so it fits
  the signal rather than the label noise.
- **Three-way stratified split, `random_state` fixed throughout**:
  `test` (20%, held out for every reported metric) / `conformal_calib` (16%,
  used only for the split-conformal threshold) / `dev` (64%, fed into
  `CalibratedClassifierCV`'s internal 5-fold cross-validation). See
  `app/ml/train.py` module docstring for why the split is three-way rather
  than the more familiar train/test.

```bash
python scripts/train_model.py                        # generates data first if needed
python scripts/train_model.py --regenerate --records 20000
python scripts/train_model.py --estimators 600 --no-cv
python scripts/check_drift.py                         # PSI/KS vs. training distribution
```

## 6. Evaluation

Measured on the held-out 2,000-record test split (`RF-v1.0-synthetic`, seed 42).
Full detail, including calibration, conformal abstention, cost-sensitive
analysis and cohort validation, lives in `docs/model-card.md` - this section
summarises.

| Metric | Value |
|---|---|
| Accuracy | **87.10%** |
| Precision (macro) | 86.75% |
| Recall (macro) | 85.80% |
| F1 (macro) | **86.24%** |
| F1 (weighted) | 87.17% |
| 5-fold CV F1 (macro) | 85.35% (+/- 1.23) |

The narrow cross-validation spread (+/- 1.23) says the result is stable, not a
lucky split. **This 87.10%/86.24% figure describes a random split** - see the
cohort (temporal) validation below before quoting it anywhere that implies
production performance.

### Per class

| Class | Precision | Recall | F1 | Support |
|---|---|---|---|---|
| Continue Using – No Changes Required | 0.79 | 0.76 | 0.77 | 312 |
| Component Recovery | 0.76 | 0.80 | 0.78 | 508 |
| Material Recovery | 0.94 | 0.93 | 0.94 | 1,129 |
| Dispose | 0.98 | 0.94 | 0.96 | 51 |

### Confusion matrix (rows = actual, columns = predicted)

CU = Continue Using – No Changes Required, CR = Component Recovery,
MR = Material Recovery, D = Dispose.

|  | CU | CR | MR | D |
|---|---|---|---|---|
| **CU** | **237** | 63 | 12 | 0 |
| **CR** | 48 | **407** | 52 | 1 |
| **MR** | 15 | 64 | **1050** | 0 |
| **D** | 0 | 3 | 0 | **48** |

Most errors are between neighbouring categories - the model occasionally
disagrees about *how much* life is left. Material Recovery and Dispose are
separated almost entirely by the material (Dispose is reserved for material
with no recovery route), so they are rarely confused with each other; this is
also why `material` is now the most important feature. The Component Recovery
row is the weakest: it sits between two neighbours on the wear scale, and for
a wire rope it is not reachable at all.

### Confidence behaviour

| Measure | Value |
|---|---|
| Mean confidence (all predictions) | 0.807 |
| Mean confidence when **correct** | 0.829 |
| Mean confidence when **incorrect** | 0.708 |

Confidence is meaningfully lower on wrong predictions - and, since the model
is now calibrated (below), that confidence number tracks observed accuracy
directly rather than being merely ordinally useful.

### Cohort (installation-year) validation - the honest number

A random split lets the model see components from every era during training.
Splitting instead by (synthetic) installation year - train on the older 70%,
test on the newer 30% - is a harder and more realistic proxy for production:

| Metric | Random split | Cohort split |
|---|---|---|
| Accuracy | 87.10% | **80.54%** |
| F1 (macro) | 86.24% | 77.44% |

The ~10-point drop is expected and is published deliberately (`models/metrics.json`'s
`cohort_validation`, also on `GET /api/v1/model/calibration`) rather than
only reporting the flattering random-split number.

### Calibration and split-conformal abstention

The Random Forest is wrapped in `CalibratedClassifierCV` (isotonic, 5-fold);
see `docs/model-card.md` §5-6 for the full reliability-bin table. Headline
numbers:

| Metric | Value |
|---|---|
| Expected Calibration Error (ECE) | **0.0134** |
| Conformal target coverage / q_hat | 90% / 0.5975 |
| Abstention rate (`DEFER_TO_INSPECTION`) | **5.9%** |
| Accuracy on the 94.1% the model answers | **89.3%** |
| Accuracy on the abstained 5.9%, if forced anyway | 51.3% |

The reliability diagram is rendered live on the Analytics page
(`GET /api/v1/model/calibration`).

### Cost-sensitive decisions

`app/ml/cost_matrix.py` is a reviewed, versioned 4x4 relative-cost table:
optimistic errors (recommending something less conservative than the truth)
cost more than conservative ones, more again on safety-critical types. Mean
expected cost drops from 0.561 (argmax choice) to 0.459 (cost-optimal choice)
on the test set - the two strategies disagree on 4.50% of decisions. Both are
reported on every prediction (`cost_analysis`); `recommendation` itself is the
result of the decision flow above (which starts from the calibrated
probabilities), and `underlying_recommendation` keeps the classifier's own
argmax, so the headline answer remains simple to audit.

## 7. Explainability

**Two layers, three global methods, all clearly labelled and never presented
as each other** (`app/ml/explain.py`, `app/ml/train.py`):

**Per-prediction (local), returned on every `/predict` response:**

1. **Blended factors** (`key_factors`). Global Random Forest feature
   importance combined with how far each reading sits from the documented
   design envelope for that component type, ranked by
   `0.55 x deviation + 0.45 x model importance` and rendered as a severity
   band (positive / low / moderate / high / critical) with a plain-language
   sentence. Fast, always available (even without a trained model).
2. **SHAP TreeExplainer** (`shap_factors`). Genuine per-prediction Shapley
   value attribution for the predicted class, computed from one
   representative fold of the calibrated 5-fold ensemble
   (`app/ml/model_registry.py::explainer_pipeline`, cached
   `shap.TreeExplainer`). A materially different, complementary signal - see
   the worked example in `docs/model-card.md` §7 where SHAP and the blended
   factors rank different features first for the same prediction.

**Global, exposed via `GET /api/v1/model/feature-importance`:**

| Method | Rank 1 | Rank 2 | Rank 3 | Bias |
|---|---|---|---|---|
| Gini (impurity) | inspection_score 26.3% | operating_hours 15.7% | load_cycles 11.9% | Biased toward high-cardinality features |
| Permutation (f1_macro drop on `test`) | inspection_score 40.7% | component_type 23.0% | operating_hours 16.6% | Unbiased, but noisier with fewer repeats |
| SHAP (mean \|value\|, 300-row sample) | inspection_score 27.5% | component_type 17.5% | operating_hours 16.0% | Additive, game-theoretically grounded |

All three agree `inspection_score` dominates - a sanity check on the
generator. Permutation and SHAP both rank `component_type` well above where
Gini puts it: exactly the high-cardinality bias Gini importance is known for.
Comparing all three, rather than reporting Gini alone, is the point.

## 8. The health score is not the model

`app/services/health_service.py` implements a separate, fully transparent
0-100 score:

1. Each reading becomes a ratio against a type-specific design envelope.
2. Ratios are clamped at 1.25 so one extreme reading cannot dominate.
3. A fixed weighted average produces a degradation index in [0, 1].
4. Preventive-maintenance adequacy grants up to 8 points of credit back.
5. `health_score = 100 x (1 - degradation_index)`.

| Factor | Weight | Factor | Weight |
|---|---|---|---|
| `vibration` | 0.16 | `repair_count` | 0.09 |
| `operating_hours` | 0.14 | `failure_history` | 0.09 |
| `inspection_score` | 0.14 | `temperature` | 0.08 |
| `component_age` | 0.10 | `average_load` | 0.06 |
| `load_cycles` | 0.10 | `days_since_last_service` | 0.04 |

The API returns the full per-factor breakdown, so a technician can see exactly
which terms cost how many points.

> **PROTOTYPE HEALTH SCORE.** This is a synthetic/demo scoring methodology. It
> is not an official KONE engineering formula and requires engineering
> validation before production use.

Keeping the score separate from the model has a practical payoff: when the
model is unavailable, the API degrades to a health-score heuristic and reports
`model_available: false` rather than failing.

## 9. The safety gate is not machine learning

After inference, `app/ml/predict.py` applies a hard rule: if `component_type`
is `Steel Rope`, `Brake` or `Governor`, the response carries
`safety_flag: true` and `safety_message: "MANDATORY HUMAN INSPECTION"`.

The gate is deliberately **outside** the model:

- It cannot be trained away by a future retraining run.
- It cannot be overridden by high confidence.
- It does not alter or suppress the model output - the UI shows
  "AI recommendation: Continue Using – No Changes Required" *and* "Human
  inspection is required before this recommendation is acted on" together.

An AI system must never autonomously authorise a safety-critical elevator
component for operation. This rule is the mechanism that makes that structural
rather than a matter of policy.

---

## 9b. Abstention is not the safety gate

`app/ml/abstention.py` applies a second, independent rule after inference:
when the calibrated top-class confidence is below 0.5, or the split-conformal
prediction set contains more than one plausible class, the surfaced
`recommendation` becomes `DEFER_TO_INSPECTION` instead of the model's argmax
class (which is still reported as `underlying_recommendation`, for audit).

This is a different mechanism from the safety gate in section 9, and the two
compose independently:

| | Safety gate | Abstention |
|---|---|---|
| Trigger | Component **type** (rope/brake/governor) | Model's own confidence/ambiguity for **this** reading |
| Can be trained away | No - a hardcoded type check | No - but its *threshold* is a modelling choice |
| Applies to | 3 of 8 component types, always | Any component type, only when genuinely ambiguous |
| Purpose | Structural: never auto-authorise safety-critical parts | Honesty: don't present a guess as a fact |

A safety-critical component can be simultaneously flagged by both: `safety_flag=true`
*and* `recommendation="DEFER_TO_INSPECTION"` if it is also a boundary case.

## 10. Limitations

1. **Synthetic training data.** Metrics describe simulated degradation. Real
   performance is unknown and could be substantially worse.
2. **The generator encodes our assumptions.** The model partly learns the
   simulator. If a real degradation relationship differs from the one modelled,
   the model has learned the wrong thing.
3. **Design envelopes are illustrative.** `TYPE_REFERENCE` values (design life,
   design hours, vibration limits) are plausible placeholders, not KONE
   specifications.
4. **Temporal generalisation is materially worse than the random split.**
   Cohort (installation-year) validation - train on the older 70% of
   (synthetic) installation years, test on the newer 30% - drops accuracy
   from 87.10% to 80.54% (§6). That is the number that should inform any
   production performance expectation. `scripts/check_drift.py` (PSI + KS per
   feature) exists to catch a live-traffic shift, but nothing schedules it
   against real traffic yet, because there is no real traffic.
5. **Point-in-time only.** The model scores a snapshot; it does not model
   degradation trajectory, and it produces no remaining-useful-life estimate
   or forecast of *when* attention will be needed (`plan.md` P2).
6. **Calibration and abstention reduce, but do not eliminate, the risk of an
   overconfident wrong answer.** ECE of 0.0134 and 90%-target conformal
   coverage are measured on synthetic held-out data; both would need
   re-validation against real removals before being relied on (`plan.md` P6).
7. **Gini importance bias**, mitigated but not eliminated by also reporting
   permutation importance and SHAP - see §7.
8. **No fairness or cohort analysis beyond installation year.** Performance
   across manufacturers, sites and regions is unmeasured.
9. **The cost matrix in `app/ml/cost_matrix.py` is illustrative**, chosen to
   demonstrate the *shape* of cost-sensitive decisioning (optimistic errors
   cost more, safety-critical types cost more again), not derived from real
   incident, warranty or liability data.

## 11. What production would require

**Data**

- Historical service records with dated, structured intervention detail
- Component removal records with the *reason* for removal
- Inspection reports with structured condition findings
- Vibration and temperature measurements, ideally as time series
- Operating hours and load/cycle counters from the controller
- Repair records with parts replaced
- Failure records including mode and consequence
- **Component-recovery outcomes** - which sub-components were recovered and
  tested, where they were fitted, and how they subsequently performed
- **Material-recovery outcomes** - material recovery yields

**Labels.** The hardest requirement. Production labels must come from validated
engineering decisions - what a qualified engineer actually decided *and* how
that decision turned out - not from a heuristic. A component left in service
that failed within a year was mislabelled, however confident the original call was.

**Process**

- Time-based validation with drift monitoring - the mechanism exists
  (cohort validation, `scripts/check_drift.py`); what is missing is real
  traffic to point it at and a schedule to run it on
- Per-class error-cost analysis - the mechanism exists
  (`app/ml/cost_matrix.py`); what is missing is a cost table reviewed by a
  quality/safety engineer against real incident data, not the illustrative
  `v1` weights
- Calibration before confidence drives any threshold - implemented
  (`CalibratedClassifierCV`); what is missing is re-validation against real
  removals
- Human-in-the-loop review for every safety-critical component, permanently
- Model versioning and full audit linkage - already implemented here, and worth
  keeping
- Regulatory review against the elevator safety standards of each market
- The full validation programme in `plan.md` P6: shadow mode against real
  historical removals, outcome capture, a pre-registered pilot

Until that exists, this remains a proof of concept that demonstrates the
workflow - now including calibration, abstention and cost-sensitivity as
worked mechanisms - not a system that should influence a real disposal
decision.
